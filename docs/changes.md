# Changes in this fork

What this fork changed on top of the reconstruction it was forked from
([opencod2/opencod2](https://github.com/opencod2/opencod2)), by area. The
per-stage history is in [ai/PROJECT_MEMORY.md](ai/PROJECT_MEMORY.md).

- **CoD2 1.3 Plus:** against a server built as OpenCoD2-Plus Server's Plus variant (`make PLUS=1`, protocol version 123) the client reads Plus snapshots, whose entity times go as offsets from the snapshot's time, and its local server writes them; the 1.3 builds define `COD2_PLUS` for the vendored code, the 1.0 ones do not. `-DCOD2_PLUS_PROTOCOL=OFF` builds stock 1.3 instead: servers any 1.3 client can join and a client that does not announce itself as Plus, with every other improvement.
- **Plus gameplay rules (Plus version 123):** against a Plus server, which plays by them for Plus clients, the client predicts what replaces zPAM's script fixes the way the server applies it (version 123 in OpenCoD2-Plus Server's plus-protocol.md); against any other server and in demos it predicts stock. **Fast reload:** a bolt-action's weapon switch taken back while the weapon still drops raises it again, and a reload that cuts a bolt-action's shot keeps the shot's time left, so switching away and back no longer fires a bolt-action sooner than its rechamber allows. **Prone peek:** going prone while leaning, the lean comes back to the prone limit as fast as a lean let go instead of halving in one frame. **MG clip:** leaving a turret keeps the player behind the gun, where using it put them, instead of taking them back to where they took it; the server places them, so the client predicts nothing new. **Climbing sound:** on a Plus server everyone hears the weapon go up as a player goes onto a ladder or into a mantle, as the climber did alone: the raise of no weapon plays `weap_raise`. **Linked view:** a player linked to a moving entity (`linkTo`, such as a mod's plane or parachute) sees from an origin lerped between snapshots, like the entity itself, instead of one that jumped with each snapshot; Pmove, the weapon and the view angles are predicted as before. Client only.
- **Plus downloads from the server itself:** a Plus server with `sv_wwwBaseURL auto` (OpenCoD2-Plus Server's plus-protocol.md, "Downloads") redirects a download to `plus:<name>`; on a Plus connection the client fetches `http://<server ip>:<port>/<name>` from the address it plays on, over the existing HTTP download, and falls back to the server's UDP download if that fails. The name must be a relative `.iwd` path, and a `plus:` URL from any other server is refused as before.
- **The Plus servers' batch of 2026-11-08:** with OpenCoD2-Plus Server 6219002, the Plus local and dedicated servers built here also rewind a player's stance animation in the antilag, so a head shot before a crouch or a prone counts; keep the votes a player cast and called across a reconnect; keep `wait` exact above 20 Hz; reset an HTTP download that moves under 1 MB in 30 s; and the bots mod joins upper floors and cellars to its waypoint graph (its cache becomes `_v3.graph`). The client predicts nothing new; the Plus version stays 123.
- **The Plus servers' batch 2 of 2026-11-08:** with OpenCoD2-Plus Server 85f92f0, the bots mod's waypoint graph holds up to 32768 nodes (`sv_graphMaxNodes`) and says so in the console when a map reaches the cap, and with `logErrors 1` the Plus local and dedicated servers print a script runtime error that repeats once and then as a count every 10 s (since 0870352 also the count left when it stops). The client predicts nothing new.
- **Plus ID:** with OpenCoD2-Plus Server 274dca1 the Plus local and dedicated servers can identify a client by a signed Plus ID and apply shared ban lists (the server repo's plus-id.md). Every client but the web one keeps an ECDSA P-256 key in `fs_homepath/plusid.key`, made on the first run and never rewritten (by rename where the home has no hard links, as on vfat or exFAT), and signs the connect challenge with it (`pk`, `ps`, `pa` in the `connect` userinfo, which servers that do not know them ignore); `plusid` prints the ID and the file to back up. A corrupt key file or a userinfo with no room for the keys connects without an ID.
- **`cl_vehicleInvertPitch`:** a vehicle mod can invert a player's mouse pitch while they fly (`setClientCvar`), without touching their archived `m_pitch`; a new map, a map restart or another server sets it back to 0.
- **Fixed shotgun spread in the local server:** `g_shotgun_spread_fix 1` (OpenCoD2-Plus Server ae124d3, CoD2x's name) puts the shotgun's 8 pellets on one of two fixed patterns, turned at random per shot. Against a dedicated server nothing changes in the client: that server traces the pellets and sends the impacts.
- **Turrets at any `sv_fps` in the local server:** with OpenCoD2-Plus Server 107f574, a Plus local server's manned MG fires at its weapon's rate, and its turrets and `trigger_hurt` keep their timing, above 20 Hz; it fired twice as fast at 40 Hz. Nothing changes against a dedicated server.
- **The Plus dedicated server sets the rate:** with OpenCoD2-Plus Server 6156d66, the Plus dedicated server built here gives every Plus client a snapshot every frame and 1,000 bytes a second per Hz (25,000 at least), whatever its `rate` and `snaps`, so `sv_fps` alone sets 20, 40 or 60 Hz; `g_forceSnaps` and `g_forceRate` take effect at once by rcon. The client sends what it did, and the local server's own client stays on loopback.
- **Antilag and killcam at 60 Hz in the servers:** with OpenCoD2-Plus Server 53281a5, the local and dedicated servers built here look up their recorded frames by the frame's length: at `sv_fps` 60 a second back was 960 ms, so the antilag placed players up to two frames late. Nothing changes at 20 or 40 Hz.
- **The antilag rewinds the pose in the Plus servers:** with OpenCoD2-Plus Server 1551c01, the Plus local and dedicated servers built here keep each player's pose per frame and put it back with the position when tracing a shot, so a head that leaned out a moment ago is hit where the shooter saw it. The client predicts nothing new.
- **64-bit clients:** `cod2_linux` and `cod2_win32.exe` build for x86_64 (`-DCOD2_X64=ON`; MinGW-w64 with `cmake/toolchain-mingw64.cmake`), run OpenCoD2-Plus Server's VM and server through the same bridge, reach the menu as the 32-bit clients do and load maps; on Linux they draw effects and light the world as the 32-bit clients do, and the Windows one plays on real Windows.
- **Name and banner:** the vendored server is named OpenCoD2-Plus Server, as that project renamed itself (it was CoD2rev-Plus); the banner and the executables' icon share its emblem, a star over "2+".
- **Graphics APIs on Windows:** the client runs on Direct3D 9 or on Vulkan through DXVK (`r_gfxApi`, in Options > Graphics), and on Direct3D 12 through D3D9On12 as an experiment, with a black screen for now.
- **The console as 1.3:** the key left of 1 opens the input line on any keyboard layout, and Shift with it the full console.
- **Builds that work again:** the Linux and MinGW builds, broken since the original was built only with MSVC, build again, and so does the WebAssembly one; `scripts/build_check.py` builds every variant in one go: Linux and MinGW (the dedicated server and, with SDL2, the client) as 1.3 and as 1.0, the 64-bit ones, the MSVC-ABI client on Windows and the web build.
- **One engine for every build:** the Windows client builds with MinGW or with Visual Studio's clang (the MSVC ABI, [ADR 0015](architecture/adr/0015-msvc-abi-client-on-the-bridge.md)) from the same sources; every client, the web one included, runs OpenCoD2-Plus Server's server, game, script VM and collision through the bridge, and the engine's own reconstructions of them were removed. Float math runs on SSE2 in every build, as that server's ([ADR 0016](architecture/adr/0016-sse2-float-math.md)): the 1.3 client rounds floats to single precision, as SSE does.
- **Compiled as C++:** on Linux and MinGW the whole engine compiles as C++ (gnu++17), with the shared headers made valid C++, without changing what it does; checks guard the C names the data blobs rely on and the structure layouts of the original binary.
- **OpenCoD2-Plus Server's script VM:** the GSC virtual machine is OpenCoD2-Plus Server's, copied unchanged into `src/script`, with a generated C/C++ bridge. The server now holds two players, disconnects, reconnects and `clientkick`, where the reconstructed VM crashed as soon as the second player joined.
- **OpenCoD2-Plus Server's server:** the dedicated server is built with OpenCoD2-Plus Server's server, copied unchanged into `src/server`, with a generated bridge in which every call between the two is checked against the engine's ABI. The local games of the Linux and Windows (MinGW) clients run on it too, and the whole client traces with its collision: a client hosts a game and others join it. With it the server refuses to send the stock and server-only `.iwd` files. Its game and bgame (`src/game`, `src/bgame`) come with it, and with them `addip` and the rotation of `games_mp.log`; in the client, cgame keeps the engine's bgame (`src/PC/bgame`), whose globals take the `eng_` prefix, and which now predicts the player's moves, mantles and weapon with OpenCoD2-Plus Server's code: in the same moves it now mispredicts (snaps back) about an eighth as often. Since then the dedicated server also runs on its core: `universal`, `qcommon` and the platform code (`src/universal`, `src/qcommon`, `src/unix`, `src/win32`), which bring the console log's rotation and timestamps, `net_strictPort` and its crash report. With its xanim (`src/xanim`, upstream's reviewed version) too, everything the dedicated server runs is OpenCoD2-Plus Server's code.
- **OpenCoD2-Plus Server's libcod:** the dedicated server is built with libcod, copied unchanged into `src/libcod` with the modules OpenCoD2-Plus Server turns on (all but MySQL): its script functions, the bots, `sv_master1` to `sv_master5`, HTTP and WebSocket (Mbed TLS), SQLite and JSON. It passes OpenCoD2-Plus Server's smoke, bots and HTTP tests in 1.3 and 1.0; the client's local games have it too, on its local server (Linux and Windows): the bots test passes there as well, and the HTTP test on Linux.
- **A dedicated server without the client's libraries:** on Linux `cod2_lnxded` needs only libc, libm, libz and libstdc++, not GL, X11, SDL2 or curl.
- **The Windows client's real lighting:** the Windows client draws with Direct3D 9 and compiles the game's own shaders with the system's d3dx9, as the original renderer does, instead of the stand-in shaders of the Mac port's GL layer (a white world and sky). The sun, the lightmaps, the models' lighting and the sky look as in the original: under Wine, next to the original `CoD2MP_s.exe` on the same spots, the two draw nearly the same picture. On the way, several of the renderer's tables that the reconstruction had left zero were filled from the original (the view weapon and players drew black, static models too), the textures load at full size again, and `r_aspectRatio` and full screen work.
- **The Linux client's real lighting:** `cod2_linux` runs the same Direct3D 9 path on DXVK native, over Vulkan, and compiles the game's shaders with vkd3d-shader ([ADR 0009](architecture/adr/0009-linux-client-on-dxvk.md), the default since [ADR 0017](architecture/adr/0017-dxvk-is-the-default-linux-client.md), also for the x64 client since [ADR 0018](architecture/adr/0018-the-x64-linux-client-on-dxvk.md)); `-DCOD2_LINUX_DXVK=OFF` builds it on the GL device.
- **Online play on modded servers:** the Windows client downloads a server's files over HTTP (`sv_wwwBaseURL`) through WinINet, as the Linux client does through curl, with the download's progress shown; before, every redirected download failed and servers that ask for it dropped the client. A mod's shell shock file that leaves out `cg_shock_viewKickFadeTime` loads, as in 1.3, instead of dropping the client. Hud elements are placed by their `horzAlign` and `vertAlign` as in 1.3 (the killcam's title and timer went to the screen's edges, centered images off screen), SD's stopwatch has its hand, and the loading screen names the gametype and the map in full.
- **A client that does not trust servers:** a server cannot run console commands, set protected dvars, write outside the game's folder or corrupt the client's memory with malformed messages; `scripts/hostile_server_test.py` sends a real client each case.
- **CoD2x's improvements, in the engine:** CoD2x patches 1.3's memory; here its options are written in the client's own code, with its dvar names (CoD2x's repository has no license, so none of its code is used): `sensitivity_MG`, `cg_drawCompass` and the compass's offsets, `cg_drawSpectatedPlayerName`, `com_writeConfig`, `cl_maxpackets` up to 125, `cl_hideServerIp` for streaming; 4096 dvars and a 512 KB command buffer, so a large `config_mp.cfg` is no longer dropped; `com_freezeWatch` (Windows) writes a report when the main thread stops; and a server whose systeminfo drops one of its two iwd lists no longer ends the session.
- **Fixes:** the server answered on the wrong port, saw no `.iwd` on Windows drives under WSL, and crashed on any kick; it announced protocol 118 in the 1.0 build; the C++ Linux build stays on glibc 2.34; `getAnimLength` and three other animation builtins no longer crash the server. The fourth or fifth map load crashed the server: the animation script grew with each map, and the error it raised from rcon corrupted the stack. The 1.0 server wrote over its own configstrings and no 1.0 client could join. Fragmented messages used the wrong offsets in both versions, and the port of a network address was where Quake III keeps it, not where CoD2 does. The `.iwd` files in the server's own folder were not searched, and the builtins that take a player did not see one with OpenCoD2-Plus Server's VM. Entities were linked into the world's sectors under the wrong number, so unlinking some of them crashed and traces tested the previous entity. In the client, every entity clipped as a box was left out of the world's sectors and the box test missed the segments that crossed it, so bullets went through the players of a local game; and since an upstream change for x64, no animation of more than one frame played on 32 bits, which left the players and the first-person weapon in a broken pose. The client crashed when it saw a player die, and its movement prediction could overrun its stack against walls; it sent a jump, a stance or a weapon change one command late and truncated the velocity it predicts; the MG42's anims, the UI's fill and text widths and a dozen other engine calls passed arguments or read results of another type than the function's, and effects played along a direction got a broken axis. No effect was drawn at all (impacts, explosions, the maps' smoke): the effects code read its flags, curve scales, colors and velocities otherwise than the original binary, scheduled delayed parts for a time that never came, left every particle at the world's origin with no second radius, and nothing drew them. A changed configstring dropped the client and the scoreboard stayed empty (the server commands' letters had other meanings), a thrown grenade hung in the air (no entity moved between its events), and snow fell only indoors (the outdoor map was upside down). On the server a player's eye, where shots start, never bobbed while walking, and would have bobbed in the air; it now bobs as 1.3's (fixed in OpenCoD2-Plus Server). Other players' animation followed a reconstruction that differed from 1.3: the animation rate went back to normal speed every frame between snapshots, turrets were tested with the wrong flags, the torso turned with the head too late or too early while aiming or firing, and a stance change blended in for the wrong time; it now follows OpenCoD2-Plus Server and 1.3. The compass never showed objectives (1.3's owner draw for them was never ported), and the end of a shellshock crashed the client (its sound was given a NULL origin). Water never moved: the wave simulation that animates it was never run. No map had a sky to the renderer (it read the wrong flags), so the sky was never added past the far plane. Aiming down the sight shook every weapon, the Bren most: the client timed the sight with the weapon's fire and rechamber times instead of its ADS transition times, so it predicted it faster than the server and was pulled back each snapshot. A message whose Huffman output outgrew its buffer overran the stack; the client and its local server now stop at the buffer, as OpenCoD2-Plus Server does.
- **Tests:** OpenCoD2-Plus Server's smoke test, unchanged, against this server, with the list of checks it does not pass yet; tests for two players, map loads, a drop error from rcon and the animation builtins; and checks for structure layouts, C names, the ABI of the bridge and the files copied from OpenCoD2-Plus Server. Tests fire level and down at a player and check that each shot lands on the upper body or on the legs, and that a knife and an explosion reach a player, on the dedicated server and in a local game.
