# Changes in opencod2-plus

Everything this fork adds to [opencod2/opencod2](https://github.com/opencod2/opencod2), in detail: the functions, files and fixes behind each item that the [README](../README.md#changes-in-this-fork) summarizes.

## Building

- **The Linux and MinGW builds work again.** The upstream changes that removed the `imp_` indirection and the GCC assembler renames were only built with MSVC, which left 119 errors on Linux and 5 on MinGW:
  - `__cdecl` and `__stdcall` are defined for GCC outside Windows (`cod2_platform.h`).
  - The Windows-only diagnostics (`_ReturnAddress`, `GetModuleHandleA`, `VirtualProtect`, `timeGetTime`, `_set_invalid_parameter_handler`) are behind `_MSC_VER`/`_WIN32`.
  - `__forceinline` on `Com_FindSoundAlias` is MSVC-only, since with GCC it left no out-of-line copy.
  - The forward declarations of `SL_ConvertToString`, `R_FinishLoadingAabbTrees_r` and `CM_SightTraceThroughBrush` match their definitions.
  - The crash handler defines `_GNU_SOURCE` for the `REG_*` indexes, and `win_net.c` uses `FD_SET`.
  - The 13 dvar slots `bg_misc.c` now defines are dropped from `src/blobs/bss.c`.
  - MinGW keeps only the 48 `--defsym` aliases whose target still exists; the other 1,925 pointed at names gone since the assembler renames were removed. The headless server gets stubs for the two display functions that live in the client-only `macos_compat.c`.
- **`long long` keeps the Windows alignment on Linux.** `COD2_WIN_ALIGN8` gives `animation_s.movetype` 8-byte alignment, so `bgs_t` matches the original binary again (`anim_user` at 740328) and its `COD2_ASSERT_FIELD` pins hold.
- **`bool` is one byte in C too**, as in C++ and in the original binary. `COD2_ASSERT_SIZE` pins `VertexProgramStreamState` (24) and `CTexUnit` (284) in both languages.
- **`scripts/build_check.py`** configures and builds `linux` (1.3), `linux-10` (1.0) and `mingw` into `build/check-<variant>/` and reports the errors. On Linux it also fails when a binary needs a glibc newer than 2.34, or when `cod2_lnxded` needs one of the client's libraries.
- **The Linux dedicated server runs without the client's libraries.** It links the same objects as the client, whose renderer, Mac GL layer, SDL2 input, crash popup and HTTP download reference GL, X11, SDL2 and curl, but it never calls them: `src/unix/linux_ded_stubs.c` stands in for them in `cod2_lnxded`, as `src/win32/win32_stubs.c` does for the MinGW server, each function returning 0. `cod2_lnxded` needs only libc, libm, libz and libstdc++.

## C++

- **The engine compiles as C++ (gnu++17) on Linux and MinGW** (`COD2_CXX_ALL`, on by default). Each C source is built through a generated wrapper, `build/<dir>/cxx_wrap/<path>.c.cpp`, that holds `extern "C" { #include "<path>.c" }`, so everything it defines or declares, block-scope `extern`s included, keeps its C name for the data blobs, the `.S` files and the `--defsym` aliases. The data blobs and the third-party libraries (speex, jpeg-6, zlib) stay C. `COD2_CXX_ALL=OFF` builds C, and `COD2_CXX_DIRS` then picks single modules.
- **The shared headers are valid C++:**
  - 128 enums declared ahead of their definitions get an opaque C++ declaration (`COD2_ENUM_DECL`) and a matching `int` base (`COD2_ENUM_INT`); `surfaceType_t` gets `unsigned int`.
  - Every project header is wrapped in `extern "C"`.
  - `test/cxx/header_check.cpp` compiles them as C++, so every `COD2_ASSERT_FIELD`/`SIZE` is checked by the C++ front end too.
- **What C allowed and C++ does not, without changing behaviour:**
  - casts for constants out of range of their `int` fields and for implicit `void *` conversions;
  - declarations split from their initializers where a `goto` jumps over them;
  - C library redeclarations replaced by their headers (133, all with the real signature);
  - `const` tables that were never given values initialized to zero, as C left them.
  - K&R imports called with arguments are declared `f(COD2_KR)`, which is `...` in C++, so the calls pass the same arguments and promotions as in C.
  - Functions that can end without a `return` (undefined in C++, where GCC drops the code after the call) return 0; in CoD2rev-Plus they are `void`.
- **Checks:**
  - `scripts/cxx_errors.py` counts the C++ errors of each module; `--return-type` finds non-void functions that can end without a return.
  - `scripts/check_c_linkage.py` lists the C++-mangled names the objects define beyond `test/c_linkage_allowlist.txt`: the 337 names the C build already defines on purpose (the original binary's C++ symbols) and the inline functions of the C and C++ library headers.
- **The C++ Linux build stays on glibc 2.34.** g++ always defines `_GNU_SOURCE`, which on glibc 2.38+ sends `strtol`, `strtoul` and `sscanf` to their C23 versions. `src/headers/glibc_compat.h`, force-included in the Linux C++ build, turns that off.

## Script VM

- **The GSC virtual machine is CoD2rev-Plus's.** `src/script` and the 24 headers it includes come byte for byte from CoD2rev-Plus `ec884b8`, at the same paths, so its later commits apply with `git am` (`COD2_PLUS_SCRIPT`, on by default on Linux and MinGW; MSVC, the web build and x64 keep `src/PC/script`). With it the server holds two players, disconnects, reconnects and `clientkick`; the reconstructed VM crashed as soon as a second player joined.
- **The bridge (`src/compat`)** connects the engine's C names with the VM's C++ ones:
  - `scripts/gen_script_bridge.py` writes `script_exports.cpp`, 95 thunks whose `__asm__` symbol is the C name the engine calls, one per function in `test/script_interface.txt`.
  - It also writes `script_imports.cpp`: 44 C++ definitions of the engine functions the VM needs, which call the engine's C symbols. Variadic ones format into a 4096-byte buffer, the size of CoD2rev-Plus's own `MAXPRINTMSG`; `Com_sprintf` formats straight into its destination, as CoD2rev-Plus's does, since a `statusResponse` can take 8192 bytes.
  - `Com_Error` never returns: CoD2rev-Plus declares it `noreturn`, and the engine's returns for `ERR_SCRIPT` and `ERR_LOCALIZATION` once the client's UI shows the error, so the bridge then raises it again as a drop. Before, a script runtime error on the client with `developer 1` ran on into unrelated code.
  - `script_missing.cpp` checks that `PROTOCOL_VERSION`, which CMake derives from `COD2_FEATURE_CFLAGS`, and `COD2_PATCH_10`, which the engine reads wherever it is set, name the same game version.
  - Return types are `decltype` of a call to CoD2rev-Plus's own declarations, so the compiler checks every thunk. Exports must return a scalar or `void`, except the two that return a struct on both sides.
  - Thunks written by hand where the two sides differ:
    - `Scr_FreeScripts(sys)` and `Scr_ShutdownSystem(sys, bComplete)` take the client binary's script system id;
    - `Scr_GetAnim` returns `scr_anim_s` in `eax`;
    - `FS_ListFiles` and `FS_FreeFileList` take an `allocTrackType` here (10).
  - `script_missing.cpp` adds what this engine lacks, as CoD2rev-Plus writes it: `Hunk_AllocXAnimTreePrecache`, `Q_rint`, `Q_vsnprintf`, `VectorCompare`, `Sys_UnimplementedFunctionInternal`, `VM_Execute` under the original binary's name, and the `"int"` string of the MinGW blob's builtin table.
- **The VM globals** (`scrVarPub`, `scrVmPub`, the parser and yacc state, `var_typename`, …) are behind `#if !COD2_PLUS_SCRIPT` in `src/blobs/bss.c`, `build/native_gen/data32.c` and `build/win_gen/data.win.S`. MinGW links with `--allow-multiple-definition`, so its blob copies would otherwise have won silently.
- **Engine side:** `GScr_PostLoadScripts` (the class maps and entity fields) runs after `Scr_PostCompileScripts`, as in CoD2rev-Plus: earlier, `Scr_AddFields` wrote over the compiled program. `Hunk_ClearHigh` is added to `com_memory.c`.
- **The game code compares script object types with the VM's values.** CoD2rev-Plus's VM adds `VAR_INT64` after `VAR_INTEGER`, so its `VAR_ENTITY` is 22, not 0x15, and every object type after it is one more. `iprintln`, `isAlive`, the sight traces and the other builtins that take an entity did not see one, and `iprintln(&"MP_CONNECTED", self)` in `tdm.gsc` raised a script error for each player who connected (with `developer 1` it stopped the map). `src/headers/scr_vartypes.h` gives the types of the VM the build uses, and `src/compat/script_missing.cpp` checks them against CoD2rev-Plus's enum.
- **The copied files follow CoD2rev-Plus `ad7f726`.** The eight CoD2rev-Plus commits since `ec884b8` that touch them applied with `git am --keep-cr`, limited to their paths (some of CoD2rev-Plus's files have CRLF line endings, which `git am` strips without `--keep-cr`). `test/vendored_files.txt` names the revision.
- **Script VM fix in the reconstructed VM** (`src/PC/script`, still used by MSVC): the per-self wait lists were kept in `levelId` and the time buckets in `pauseArrayId`, one field off from the rest of the VM, so kicking or dropping a player with a `waittill` running crashed the server.

## Server

- **The dedicated server is CoD2rev-Plus's.** `src/server` comes byte for byte from CoD2rev-Plus `ad7f726` (`COD2_PLUS_SERVER`, on by default with `COD2_PLUS_SCRIPT`). `cod2_lnxded` and `cod2_win32_ded.exe` link it instead of `src/PC/server_mp`, which the client keeps for its local server: on Linux `server_mp` is its own object library, and `bss.c` and `data32.c` are compiled for each executable. In the dedicated server they leave to `src/server` the 48 globals it defines (`sv`, `svs`, the `sv_*` dvars, `rcon_password`, `nextmap`, `gameInitialized`, `actorLocationalMins`, `sv_serverId_value`…); `data.win.S` does the same and leaves out `server_mp`'s client command table.
- **The bridge (`src/compat/server_*.cpp`)** is generated like the script VM's (`scripts/gen_script_bridge.py --module server`): 66 exports, the `server_mp` functions the rest of the engine calls (`test/server_interface.txt`), and 205 imports. It joins the objects of the Linux and MinGW builds, since the unoptimized MinGW objects keep calls that `-O2` drops with unused static functions.
- **Every crossing is checked against the engine's ABI.** `scripts/engine_abi.py` reads with gdb the debug information of a binary built with `server_mp` and writes `test/server_abi.txt`: the class and size of each function's return and the stack slot of each parameter. Each thunk asserts its CoD2rev-Plus declaration against it. A void import of an integer is accepted, a void import of a float is not (it would stay on the x87 stack), and an integer return the two sides give different sizes travels as the engine's. No crossing function is `regparm`.
- **Thunks written out where the two sides differ:**
  - `SV_SightTrace` returns `*hitNum`, which the engine reads and CoD2rev-Plus leaves in its argument;
  - `SV_XModelDebugBoxes` takes the engine's entity and ignores it;
  - `SV_GetClientPositionAtTime` is `SV_GetClientPositionsAtTime` in CoD2rev-Plus;
  - `SV_AddDedicatedCommands` is empty: CoD2rev-Plus's `SV_AddOperatorCommands` registers `say` and `tell` itself when the server is dedicated;
  - `MSG_ReadBitsCompress` decodes with the engine's function, which has no bound on its output, into a buffer for any input, and copies at most `toSizeBytes`, keeping CoD2rev-Plus's bound on compressed client messages;
  - `FS_Shutdown` gets `closemfp` 1, as `server_mp` passed, and `MSG_WriteBigString` the engine's four unused arguments; `MSG_ReadDeltaPlayerstate` and `MSG_WriteDeltaPlayerstate` drop the one CoD2rev-Plus does not use.
- **`src/compat/server_missing.cpp`** has the CoD2rev-Plus functions this engine lacks, from its sources: `BigShort`, `I_strcmpConstantTime`, `SnapAngles`, `Cmd_ReplaceControlChars`, `DObjSetRotTransIndex`, `DObjSetControlRotTransIndex`, `FS_VerifyIwd`, and `MSG_ReadString` and `MSG_ReadStringLine`, which take a buffer and clean the characters they read where the engine's return a static buffer.
- **Structures.** In 1.3 the server's structures match the engine's. `dvar_s` is 72 bytes there (vectors in line) and 36 here, but the server reads only `current` and `modified`, at the same offsets. In `netchan_t`, `dropped` and `incomingSequence` are swapped; the server reads neither. In 1.0 CoD2rev-Plus keeps the 1.3 forms of `client_t`, `serverStatic_t` and `challenge_t`, which nothing outside the server touches.

## Game

- **The dedicated server runs CoD2rev-Plus's game and bgame too.** `src/game` and `src/bgame` come byte for byte from CoD2rev-Plus `ad7f726`, with `src/stringed/stringed_public.h`, and join `src/server` in `cod2_plus_server`: `COD2_PLUS_SERVER` now means server, game and bgame. The client keeps `src/PC/game_mp`, `src/PC/game` and `src/PC/bgame` with `src/PC/server_mp`. The server and the game call each other directly in C++, so the 24 thunks between `src/server` and `src/PC/game_mp` are gone, and the VM calls the game directly.
- **The bgame comes with the game** because the two sides cannot share `level_bgs`: the engine's bgame reaches it through `bgs`, which only `src/PC/game_mp` set, and its `animation_s` keeps the Windows layout (104 bytes, `COD2_WIN_ALIGN8`) where CoD2rev-Plus's is packed (96), as in `cod2_lnxded`. With the engine's bgame, `BG_LoadAnim` crashed at the first map.
- **The bridge** (`--module server`) reads the game's and bgame's objects too: 122 exports and 285 imports. The exports add the 8 game functions and the 48 bgame functions the engine calls by their C names, through `bgame`'s callers in cgame and `client_mp`, linked but not run in the dedicated server, `common.c` and the blobs' `imp_` pointers. The VM is shared by the client and the dedicated server, so its four calls into `src/PC/game_mp` (`Scr_GetFunction`, `Scr_GetMethod`, `Scr_GetObjectField`, `Scr_SetObjectField`) moved to `src/compat/client_script_imports.cpp`, which only the executables without CoD2rev-Plus's game link.
- **Thunks written out:** `G_AnimScriptSound` returns 0 and `G_RegisterWeapon` nothing, as `src/PC/game_mp`; `BG_IsPlayerWeaponAnAlt`, which only cgame calls and CoD2rev-Plus lacks, has `src/PC/bgame`'s body; `DiffTrackAngle` gets the engine's three unused arguments; `Hunk_ClearLow` is the engine's `Hunk_ClearToMarkLow`.
- **`server_missing.cpp` adds** `Com_BitCheck`, `Com_BitSet`, `Com_BitClear`, `VectorInverse`, `VectorLength`, `Vec2Length`, `Vec2LengthSq`, `VectorLengthSquared`, `Vec3Lerp`, `RoundFloatArray`, `SetConfigString`, `SetConfigString2`, `FS_RotateHomeFile` and `FS_HomeFileLength` (which reads the size through stdio: the engine has no `FS_FileOpenReadBinary`). `G_GetEntityToken` left it: the game defines it.
- **The blobs leave the game's and bgame's globals to them in the dedicated server:** 114 in `bss.c` (the `g_*`, `player_*`, `jump_*` and `mantle_*` dvars, `level`, `g_entities`, `g_clients`, `level_bgs`, `bg_weaponDefs`…), `playerMins`, `bulletPriorityMap`, `bg_iNumWeapons` and `controller_names` in `data32.c`, and `bg_numItems` in `literals32.c`, now compiled for each executable. On MinGW, `data.win.S` leaves out 45 tables: those the game or bgame defines and those that point into `src/PC/game_mp` or `src/PC/bgame` (`functions`, `methods`, `spawns`, `entityHandlers`, `pmoveHandlers`…), and `literals.win.S` leaves out `bg_numItems`. MinGW links with `--allow-multiple-definition`, so a blob left defining one of them would win without an error: `scripts/check_duplicates.py`, which `build_check.py` runs on every variant, fails when the dedicated server gets a C name both from CoD2rev-Plus and from the engine.
- **Structures.** `level_locals_t`, `gitem_s`, `scr_const_t` and `game_hudelem_s`, which the engine still reads, match field by field in 1.3 and 1.0, and `scr_data_t` and `entityHandler_t` by size.

## Core and platform

- **The dedicated server runs on CoD2rev-Plus's core.** `src/universal`, `src/qcommon`, `src/stringed/stringed_hooks.cpp`, the platform code (`src/unix` on Linux, `src/win32` on MinGW, with `src/ui/keycodes.h`) and zlib's `unzip.c` and `ioapi.c` come byte for byte from CoD2rev-Plus and join `cod2_plus_server`. The dedicated server starts in CoD2rev-Plus's `main`. With them come the console log's `logfileName`, `logfileRotate` and `logTimestamps`, `sv_logRcon`, `net_strictPort`, the crash report in `crash.log`, and CoD2rev-Plus's dvars, hunk, file system, commands, network and collision.
- **One copy of each state.** `test/plus_replaces.txt` lists the engine sources CoD2rev-Plus replaces in the dedicated server: the server, game and bgame of the earlier phases and every source that holds state CoD2rev-Plus's copy also holds (`dvar.c`, `com_memory.c`, `com_files.c`, `common.c`, `cmd.c`, `files.c`, `msg_mp.c`, `net_chan_mp.c`, the `cm_*` files, `dobj_management.c`, `stringed_hooks.c`, `unzip.c`, `surfaceflags.c`, and the Mac, win32 and Linux platform files). CMake moves them to `cod2_server_mp`, which only the client links. Sources without state (`com_math.c`, `q_shared.c`, `q_parse.c`) stay: each side keeps its own. `scripts/check_single_impl.py`, which `build_check.py` runs, fails when an engine object of the dedicated server still defines a function the bridge exports.
- **The bridge** now has 324 exports and 71 imports: the 261 functions of the replaced sources that the rest of the engine calls, of which CoD2rev-Plus has 197 (31 that it defines without declaring are in `src/compat/server_decls.h`). `FS_FileOpen`, `FS_FileRead`, `FS_FileWrite`, `FS_FileClose`, `FS_Remove`, `FS_TouchFile`, `FS_FileExists`, `FS_ListFiles`, `FS_FreeFileList` and `Hunk_ClearTempMemory` are written out from `src/PC` on CoD2rev-Plus's file system and hunk (`unzip.c` opens the iwds through `FS_FileOpen`). The 73 in `test/server_fatal.txt`, which CoD2rev-Plus lacks or has with another signature and which only cgame, client_mp, gfx, ui, the sound driver, the player profile or the blobs' `imp_` pointers call, stop the server with their name if one ever runs.
- **The VM's bridge** moves its calls into what CoD2rev-Plus's core defines (and the four functions of `script_missing.cpp` it has) to `src/compat/client_script_*.cpp`, which only the executables without it link. The generator spells `FILE` the same on glibc and MinGW.
- **dvar_s** is CoD2rev-Plus's (72 bytes) in the dedicated server. The engine code there that can run reads only `name`, `flags`, `type`, `modified` and `current`, at the same offsets.
- **The blobs** leave CoD2rev-Plus 86 more globals in `bss.c`, `cmd_text` and `kbitmask` in `data32.c`, and `bytedirs` and the origins in `com_math.c`, now compiled for each executable; `data.win.S` leaves out 106 tables, guarded in one pass from the original, and `win32_stubs.c` two stubs. The strings and variables of the replaced sources that the blobs or the client's code still name are in `src/compat/server_data.cpp`.
- **CoD2rev-Plus `c75d325`:** the copied files follow it. `Com_Error` there now ends the rcon redirect before its longjmp, as `src/PC/qcommon/common.c` already did here: with CoD2rev-Plus's `common.cpp` the error message of `rcon error drop` was written into the freed buffer on `SVC_RemoteCommand`'s stack and lost.
- **xanim too.** `src/xanim` comes from CoD2rev-Plus and `src/PC/xanim` joins `test/plus_replaces.txt`. With the core already in, it needs nothing from the engine: the server's bridge has no imports left, so everything the dedicated server runs is CoD2rev-Plus's code. The engine names 70 xanim functions, only from code the dedicated server does not run (cgame_mp, gfx_d3d, EffectsCore, client_mp, the blobs' `imp_` pointers): 64 are exported, and the 3 CoD2rev-Plus lacks and the 3 it has with another return type are in `test/server_fatal.txt`. `src/compat/server_missing.cpp` is gone, and the engine's `dobj.c` no longer prints its `[ckpt]` lines in the dedicated server.
- **Variadic exports** (`Com_Printf`, `Com_DPrintf`, `Com_Error`, `FS_Printf`) format the engine's arguments and pass them on as `"%s"`; they used to pass the format alone, so a missing model was reported as `xmodel '' not found`.

## Client

- **The Linux client's local games run on CoD2rev-Plus's server.** With `COD2_PLUS_CLIENT_SERVER` (on by default on Linux), `cod2_linux` links CoD2rev-Plus's server, game and bgame, built with `LISTEN_SERVER`, on the engine's core and xanim, through its own bridge (`--module client_server`: the 25 functions of `test/client_server_interface.txt` the client calls, and 293 imports into the engine). `src/PC/server_mp`, `src/PC/game_mp` and `src/PC/game` leave the Linux client; MSVC, the web build, x64 and the MinGW client still use them. A client hosts a game and another one joins it, in 1.3 and 1.0.
- **CoD2rev-Plus `e365a09`:** `LISTEN_SERVER` keeps `DEDICATED` undefined, so its server builds its `#ifndef DEDICATED` code, and `SV_SpawnServer` and `SV_Shutdown` get the client calls of the Windows binary (`CL_InitLoad`, `CL_MapLoading`, `CL_ShutdownAll`, `CL_StartLoading`, `CL_Disconnect`). Without `CL_ShutdownAll` the menu's renderer stayed up while the map loaded, and `Image_Register` read freed memory; without `CL_MapLoading` the local client never joined. Its own builds are unchanged.
- **Two bgames.** cgame keeps the engine's bgame, which reaches its animation state through `bgs`; the local server runs CoD2rev-Plus's, which uses `level_bgs` and another `animation_s`. The 67 engine bgame globals both define get the `eng_` prefix: `scripts/bgame_names.py` writes `src/headers/engine_bgame_names.h` from `test/engine_bgame_names.txt`, which `common_types.h` includes, and renames the MinGW blobs' labels; the dedicated server, which has no engine bgame, gives the `imp_` pointers placeholders (`src/compat/server_bgame_names.cpp`). `bg_itemlist`, `bg_numItems` and `scr_const` stay shared, as in the original binary.
- **What cgame no longer shares with a local server:** it creates its own mantle anims and loads its own weapons, as with a remote server, and the local server marks and frees its weapon defs with its own `Com_SetWeaponInfoMemory` and `Com_FreeWeaponInfoMemory` (`client_server_missing.cpp`): with the engine's, a full `map_restart` stopped on `BG_IndexForString: unknown token 'springfield'`.
- **The blobs' guards** split in two: `COD2_PLUS_GAME` for what CoD2rev-Plus's server, game and bgame define (the dedicated server and the Linux client) and `COD2_PLUS_SERVER` for what its core defines (the dedicated server).
- **The VM's thunks into the engine** come in two groups (`script_game_imports.cpp`, `script_core_imports.cpp` with `script_core_missing.cpp`), linked by the executables without CoD2rev-Plus's game or core.
- `build_check.py` runs `check_duplicates.py` and `check_single_impl.py` on `cod2_linux` too. The client's ABI is read from a client built with `-DCOD2_PLUS_CLIENT_SERVER=OFF`, since the bridge's C++ thunks shadow the engine's functions in gdb.

## Fixes

- **Replies went to the wrong port.** `Sys_GetEvent` queued only the first 12 bytes of a packet's `netadr_t` and `Com_EventLoop` read the data from byte 12, so the port came from the packet itself: every reply to `getinfo` went to port 29801 ("ti" of "getinfo"). Both use `sizeof(netadr_t)`.
- **Game files on Windows drives under WSL.** Linux builds with `_FILE_OFFSET_BITS=64`: the 32-bit `readdir` failed with `EOVERFLOW` on file systems with large inode numbers, so no `.iwd` was found.
- **Protocol of the 1.0 build.** The server announced, registered and required protocol 118, and the client sent it, also in the 1.0 build; `COD2_PROTOCOL_VERSION` is 115 for 1.0 and 118 for 1.3.
- **The fourth or fifth map load crashed the server.** `BG_AnimParseAnimScript` appended the player animation script to `level_bgs.animScriptData` and nothing cleared it between maps: each `map` (not `map_restart`) added about 700 items, and the third one went over 2048 and raised `Com_Error`. `G_InitGame` now clears it, as CoD2rev-Plus does. The client was not affected: `CG_Init` clears all of `cg`.
- **A drop error raised by an rcon command corrupted the stack.** `SVC_RemoteCommand` redirects the output into a 16 KB buffer on its own stack, and `Com_Error` longjmps to `Com_Frame` without ending the redirect: `Com_ErrorCleanup` and the `Com_Printf` of the error message ran over that buffer, and appending the message overwrote their return addresses (`eip=0`). `Com_Error` now flushes the redirect while the buffer is valid, so the rcon client also gets the output up to the error. CoD2rev-Plus does not end it either.
- **The 1.0 server wrote over its configstrings.** `bss.c` reserved 41216 bytes for 1.0's `svs`, whose `serverStatic_t` is 0xc108: the end of `challenges`, `redirectAddress`, `authorizeAddress` and `tempBans` landed on `sv`'s first configstrings, and an rcon command made the next `SV_Shutdown` or `map_restart` free `0x4`. `sv` and `svs` have their types in every build.
- **Fragment offsets.** 1.0 sends them as shorts in both directions; 1.3 as longs in both, as `CoD2MP_s.exe` 1.3 writes the DWORD whatever the socket (`Netchan_TransmitNextFragment` at `0x447e61`). The reconstruction used longs only from the server socket, so no 1.0 client could put the gamestate together, and a fragmented 1.3 client message, such as a long userinfo, did not reach the server.
- **The port of `netadr_t` follows the IP.** The header kept it at 0x12, after the IPX address, as Quake III does; `NET_AdrToString` in `CoD2MP_s.exe` 1.3 (`0x44770a`) reads it at +8, as CoD2rev-Plus does. The engine reaches it by name, but a `netadr_t` crossing to CoD2rev-Plus's server had its port read and written over the IPX bytes.
- **The home folder of the game is searched too.** `FS_Startup` added `fs_homepath` only for `fs_basegame` and `fs_game`, so `.iwd` files in the server's own `main` folder were not in the search path; CoD2rev-Plus, from the Linux binary, and Quake III add it when it differs from `fs_basepath`. CoD2rev-Plus's server checks a download against the search path (`FS_VerifyIwd`, CVE-2006-2082).
- **The home folder gets its directories.** `FS_CreatePath` made a directory only at each `\`, but `FS_BuildOSPath` joins with `/`, so on Linux nothing under `fs_homepath` was created: the server could not open `games_mp.log` or write its config, and the client could not create `hunkusage.dat`, whose `Com_Error` sent it back to the menu after loading the map. It now splits at both.
- **Entities in the world's sector lists.** `CM_InsertEntityIntoWorldSector` stored an svEntity's index and walked the list with it, while `CM_UnlinkEntity` and the traces read the list as numbers plus one (0 ends it), as the binary does (CoD2rev-Plus's `CM_AddEntityToNode`). Unlinking the first entity of a sector walked off the list and crashed, the traces tested the previous entity, and entity 0 could not be linked; the client's local server had the same lists. CoD2rev-Plus's game deletes entities when its gametype starts, which crashed the dedicated server.
- **Bullets went through the players of a local game.** Three bugs of the engine's collision and xanim, which the client's local server runs, and which the dedicated server, on CoD2rev-Plus's, never had:
  - `CM_InitBoxHull` left the box model's `brushContents` at 0, where the binary, CoD2rev-Plus and Quake III give it -1. `CM_LinkEntity` takes an entity's link contents from its clip model, so every entity clipped as a temporary box (players, items) was unlinked from the world's sectors: no trace, explosion or trigger found it.
  - `CM_TraceBox` tested the max planes with the min planes' sign (-1) and returned a miss whenever the exit fraction shrank, so a segment through a box was taken as missing it. It follows CoD2rev-Plus's now: the min planes with the sign -1, then the max planes with 1.
  - With the frames read again (below), a bone with an animated translation lost the model's offset: `DObjCalcAnim` gave a child bone the model's translation only when no anim moved it, and `DObjCalcSkel` did not add it. As in CoD2rev-Plus and the binary, the first now leaves it at zero and the second adds the model's translation to every child bone before composing it with its parent. Bones turned by a controller (`DObjSetControlTagAngles`: a player's head and torso, a turret's aim) get the offset too.
- **No animation of more than one frame played on 32 bits.** Upstream `acccfb7` guarded the animated quat and trans channels of `XAnimCalc` against a frames pointer below 4 GB, seen as corrupt data on x64; on 32 bits every pointer is below 4 GB, so every channel with more than one key was skipped. The players' bones got zero quaternions (they collapsed to their origin in the client's view and in the local server's traces) and the first-person weapon was drawn in a broken pose. The guards are x64 only now.
- **The crash report lists the top of the stack** on 32-bit Linux, the only way back to the caller when `eip` is bad.
- **MinGW client:** it includes `<GL/gl.h>`, since calling the `__stdcall` GL functions through implicit `cdecl` declarations left the stack unbalanced. The `ioctl` stub returns -1 instead of whatever was in `eax`.

## Tests

- **Smoke test:** `scripts/smoke_test.py`, `cod2client.py` and `cod2snap.py` are copied unchanged from CoD2rev-Plus. `scripts/opencod2_smoke.py` runs the smoke test against this server and compares its failures with `test/smoke_expected_failures_<protocol>.txt`. It fails on a new failure and on a listed one that now passes, so the lists only shrink. `test/smoke_flaky.txt` holds the checks whose result depends on timing with this server.
- **Local games:** `scripts/listen_test.py` starts a client with `+map` and another with `+connect`, and checks with rcon that the local server holds both (the host on loopback), that `g_speed` from the command line survives the game's registration, and that both are back after a `map_restart` and a `map` to another map. It needs a CD key in `~/.cod2/preferences` and is skipped without one.
- **Two players:** `scripts/two_players_test.py`, with `developer 1` so that a script error stops the map and fails the test. It also checks that `g_speed` set on the command line survives the game's registration, and that a `games_mp.log` under `g_logRotateSize` is not rotated.
- **Map loads:** `scripts/map_reload_test.py` loads maps by rcon, alternating `map_restart` and `map` between `mp_toujane` and `mp_carentan`. **Drop errors:** `scripts/rcon_drop_test.py` raises one with `rcon error drop` (`developer 1`).
- **Animation builtins:** `scripts/anim_builtins_test.py` runs `getAnimLength`, `animHasNotetrack`, `getMoveDelta` and `getAngleDelta` from a test mod.
- **Hit locations:** `scripts/hit_location_test.py` writes a dm gametype that spawns a target and, a few steps in front of it, a minimal client with a semi-automatic rifle that fires level, at the head, and then 15 degrees down, at the legs; the mod logs the hit location of each hit, which must be in the body parts of its aim (the upper body for a level shot, since a host standing idle sways). The target is a minimal client on the dedicated server, or with `--listen` the client hosting the game (with a CD key).
- **Contact:** `scripts/contact_test.py`, with the same minimal client, picks phases by rcon (`contact_phase`): it walks into the target and must stop at a body's width, walking at it again it must set off a `trigger_radius` on its way, its knife must hit it with `MOD_MELEE`, a frag grenade it throws must hit it with `MOD_GRENADE_SPLASH`, and the mod's `radiusDamage` must reach it with `MOD_EXPLOSIVE`; on the dedicated server or, with `--listen`, in a local game.
- **Layout parity:** `scripts/layout_parity.py` compiles a program with this repo's headers and one with CoD2rev-Plus's and compares sizes and offsets of the types in `test/layout_parity_types.txt`: those the script VM, the server and the game share with the engine, in 1.3, 1.0 and MinGW. Nothing is run: each side's values are an array in a section of its own of the compiled object, which `objcopy` reads, so MinGW needs no Wine.
- **One copy of each state:** `scripts/check_single_impl.py <build> <target>` lists the engine objects that still define a function `test/server_interface.txt` exports.
- **Names defined twice:** `scripts/check_duplicates.py <build> <target>` lists the C names a target gets both from CoD2rev-Plus's objects and from the engine's.
- **Renamed bgame globals:** `scripts/check_bgame_names.py <build>` preprocesses each engine source of `compile_commands.json` that names one of `test/engine_bgame_names.txt` and lists where the plain name is left, which would link to CoD2rev-Plus's global instead of the `eng_` one. `scripts/build_check.py` runs it for the Linux client.
- **Copied files:** `scripts/vendor_check.py` compares every file in `test/vendored_files.txt` with a CoD2rev-Plus checkout.
- **Unit tests** for the scripts: `python3 -m unittest discover -s test`.

## Known problems

- What CoD2rev-Plus has in libcod is not here: its script functions, the bots and `sv_master1` to `sv_master5`, so the server sends its heartbeat only to the Activision master and the smoke test's `heartbeat sent to sv_master1` fails.
- The MinGW client, MSVC, the web build and x64 keep `src/PC/server_mp`, `src/PC/game_mp` and `src/PC/game`.
- A client started with `dedicated 1` frees the FX system and does not create it again, as the engine's server did; and CoD2rev-Plus's `SV_Shutdown` does not clear `com_errorEntered` when a local map load is cut short, so a second error during that cleanup is fatal instead of a drop.
- The MinGW dedicated server builds with CoD2rev-Plus's server, game, bgame, core and `win32` platform code, and its types match CoD2rev-Plus's (`scripts/layout_parity.py --variant mingw`), but it has not been run (no Wine here).
- The MSVC build is not checked by the scripts above and still compiles C with the reconstructed VM and server.
